# ConfigPilot 创新点与实现方案

更新日期：2026 年 11 月 17 日

本文说明面向服务网格配置验证的研究目标、方法及实现。接口与支持范围见 [架构](ARCHITECTURE.md) 与 [实现核对表](IMPLEMENTATION_STATUS.md)。

## 1 研究主线与目标

ConfigPilot 面向服务网格配置的生效全过程，检查声明意图是否被正确实现为数据面规则和运行行为，并降低验证的执行代价，解释异常涉及的配置、策略和服务。

方案包括四个部分：全链路验证、跨层统一语义模型、低开销验证规划，以及配置依赖图与诊断。下文分别说明它们解决什么问题、怎样实现、如何配合，以及已有实现和后续工作的边界。

这里的“全链路验证”沿着“声明配置 → 已安装规则 → 运行行为”组织检查。它不表示已覆盖全部 Istio 功能，也不表示已完整验证配置创建、更新、删除等所有生命周期场景。

## 2 挑战与创新点概览

| 挑战 | 方法 | 主要回答的问题 |
|---|---|---|
| 配置在不同阶段可能以不同方式失效，证据和判定条件不同 | 面向服务网格配置的全链路验证 | 验证哪个环节，依据什么判定 |
| 声明配置、代理规则与运行行为的表示不同，组合执行语义难以直接对齐 | 跨层统一语义模型 | 如何统一解释并比较跨层语义 |
| 重复执行、重复采集和等待开销大，直接合并又可能掩盖故障 | 低开销验证规划 | 哪些工作可以复用，哪些任务可以并发 |
| 配置、策略和服务依赖交织，异常证据分散 | 配置依赖图与诊断 | 异常可能来自哪里，影响哪些对象 |

四项方法的职责分别是：确定验证边界、解释有效行为、安排验证工作、关联异常证据。论文需要分别给出方法和实验依据，不能仅将四个系统模块并列作为创新证明。

### 2.1 四项创新与五模块的对应关系

| 创新点 | 主要模块 | 实现联系 |
|---|---|---|
| 全链路验证 | 采集、解析、判定为阶段检查基础，规划与执行用于运行验证 | 保留独立静态结论和动态义务结论，按同一策略、作用范围和版本关联 |
| 跨层统一语义模型 | 解析为核心，规划和判定共同使用 | 统一解释声明期望与受支持的数据面语义，为验证期望、比较和证据归因提供来源 |
| 低开销验证规划 | 规划、执行、采集 | 分别减少重复探针、冲突排队和重复证据读取 |
| 配置依赖图与诊断 | 解析、判定，并向规划提供依赖切片 | 建立配置、策略、服务关联，连接阶段差异、失败义务及执行证据 |

五模块是工程职责划分，四项创新是方法贡献。采集、解析、判定由静态与动态路径共用；规划和执行主要提供动态验证能力。CLI、Web 和编排作为公共支撑。

## 3 创新点一 面向服务网格配置的全链路验证

### 3.1 解决的问题

声明配置正确，不代表数据面安装正确；数据面安装了相关规则，也不代表运行时满足触发条件后会产生预期行为。配置传播尚未收敛、故障没有触发、证据不完整和真实配置错误，还可能表现得相似。

因此，需要把各阶段的检查连接起来，并明确什么证据足以支持结论。

### 3.2 实现方式

第一阶段比较声明期望与已安装规则。期望来自管理员声明的参照配置，实际状态来自数据面快照。检查既包括期望行为是否缺失或被错误实现，也包括实际是否存在额外的非预期有效行为。

第二阶段根据声明期望生成动态验证义务，发送能够触发目标行为的请求，收集实际执行证据，再逐项判断。不能只因为找到了相关规则，就认为策略已经通过动态验证。

全链路验证对应两条路径：

```text
静态：采集声明与数据面快照 → 解析、建模与对齐 → 静态判定
动态：声明参照 → 规划 → 执行 → 采集运行证据 → 动态判定
衔接：按同一策略、作用范围及配置版本关联两阶段结论与证据
```

判定模块分别保存静态结论和动态结论。静态发现缺失或错误规则时，即使部分运行样本通过，也不能抹去该差异；静态检查通过而动态证据不足时，仅能确认对应配置实现检查已完成。动态期望始终来自冻结声明，不从错误的数据面规则重建。

当前静态对齐与动态义务判定均有独立入口，但 `run_validation()` 主要组织动态部分。同一运行内的阶段身份映射、版本关联和统一结果汇总还需要接通；“先解析静态产物再执行探针”本身不足以证明完成全链路结果关联。

针对不同策略定义不同的 Runtime Oracle，即运行时判定方法：

| 策略 | 必要触发与观测 | 判定重点 |
|---|---|---|
| 路由与 Header 操作 | 确认选中目标规则，记录实际目标及报文字段 | 请求是否到达正确目标，字段是否按预期变化 |
| 加权分流 | 足够样本、完整目标回执及统计方法 | 分配比例是否在事先规定的统计范围内 |
| 重试与超时 | 可控失败或延迟、尝试事件、请求起止时间 | 重试恢复与总预算是否分别满足要求 |
| 连接池等状态策略 | 足够负载、状态隔离及可归因的代理证据 | 是否出现被测试的状态变化或拒绝行为 |

判定统一保留 PASS、FAIL 和 INCONCLUSIVE。后者表示触发、适用范围或证据不足，不应被当作通过，也不能从验证义务中删除。

### 3.3 需要体现的贡献与边界

贡献重点是分阶段检查的衔接、策略专属判定和证据解释，而不只是同时使用静态与动态工具。

只比较声明配置与最终 Envoy 快照时，可以发现两者不一致，但未必能够区分翻译错误与下发错误。进一步定位这两个过程，需要额外的中间状态证据。配置版本、采集时间和收敛状态也应参与结果解释。

## 4 创新点二 跨层统一语义模型

### 4.1 从单策略属性扩展到组合行为

保留 PAOC 四元组描述单条策略的匹配条件、动作、作用范围和约束参数。策略范围继续使用原模型中的信息，不再另外引入重复的“上下文”维度。

模型以 PAOC 表达单策略属性，并补充规则顺序、引用和联合约束等策略关系，可表示为：

```text
统一语义模型 = 策略单元集合 + 策略关系集合 + 受支持的语义解释规则
```

策略单元说明一条规则是什么，策略关系说明多条规则如何选择、引用、覆盖和共同约束执行。

### 4.2 具体怎样增加关系

首先保留每条策略的资源身份、规则身份和字段来源。例如，不能只记录“reviews 服务存在重试和超时”，还要记录它们分别属于哪个 VirtualService 的哪条 HTTP 规则。

然后从原始配置结构和明确引用中提取关系：

| 关系 | 示例 | 对验证的作用 |
|---|---|---|
| 选择顺序 | 同一规则列表中 p1 在 p2 前面 | 判断后序规则是否被遮蔽，生成有效触发请求 |
| 规则附着 | 重试、超时和 Header 操作属于同一条路由 | 保留共同生效的指令，分析整个执行范围 |
| 引用绑定 | 路由引用 Service、Gateway 或 subset | 检查依赖是否解析，并加入行为依赖切片 |
| 继承覆盖 | 基础设置与局部设置存在覆盖关系 | 计算最终有效参数，避免比较未生效的原始值 |
| 联合约束与潜在截断 | 多个策略共享时间预算，或某动作提前结束执行 | 阻止无依据的探针替代，并生成针对性交互验证 |

关系需要保存参与者、条件、来源和语义版本。未支持字段、未解析引用和未知关系必须显式保留。没有提取到关系，不能直接解释成不存在关系。

### 4.3 一个简单例子

```text
p1  匹配 /api/admin  转发到 admin
p2  匹配 /api        转发到 general
关系  p1 在 p2 之前  两者属于同一个 first-match 选择组
```

对这类选择组，p2 的有效条件不仅是匹配 `/api`，还包括没有被 p1 匹配。交换 p1、p2 后，即使策略属性集合没有变化，`/api/admin` 的实际选择也可能改变。

关系解析器需要将这种差异转为可比较的有效行为，以及能够暴露差异的动态请求。不同资源中的局部索引不能直接拼成全局优先级。

### 4.4 当前代码与后续实现

方案由 parser 从原始快照构造关系参照模型，并写入 `aligned_semantic.json` 的 `relational_model`。它避免了按服务聚合后丢失具体路由归属的问题；PAOC 和对齐产物继续保留兼容。

后续还需要将受支持的数据面关系投影到同一表示，比较两层的有效行为。不能把节点或关系数量相等当作语义等价，也不能把合法生成规则或不可达冗余条目一概判为异常。

当前字段级继承解析、全部数据面关系投影和完整双向行为等价检查尚未完成，不能在论文中写成已全面实现。

## 5 创新点三 低开销验证规划

### 5.1 解决的问题与基本原则

动态验证的代价不仅是探针数量，还包括配置准备和恢复、实际请求、遥测读取、等待和冲突排队。降低代价需要联合安排这些工作。

我们保留 if、what、when、where 描述测试场景，但先生成逻辑验证义务，再规划实际执行。每项义务明确触发条件、行为断言、证据需求和执行前提。

执行合并采用“默认独立，满足条件才复用”。独立探针仍然面对实际策略组合，不表示删除环境中的其他策略，也不表示所有任务必须串行执行。

### 5.2 三种不同的优化

| 优化 | 具体做法 | 必须保持的条件 | 节省什么 |
|---|---|---|---|
| 探针复用 | 同一请求或批量执行支持多个验证义务 | 有效触发、执行前提和各自判定均得到保持 | 重复请求和重复执行 |
| 采集共享与证据复用 | 汇总采集需求，同一记录支持多个断言 | 来源可追溯，证据可归因且完整 | 重复查询、读取和处理 |
| 冲突感知调度 | 先检查任务能否同时运行；有冲突的排队，等待观测的暂时让出线程，让其他可运行任务继续 | 不互相改动所依赖的配置，不扰动共享状态，不超过负载范围，观测结果能分别归因 | 减少线程被排队和等待占用，缩短总完成时间 |

采集兼容不代表探针可以复用，探针可以复用也不代表任务可以任意并发。共享服务级聚合指标如果仍不能区分来源，就必须保留相应观测隔离。

### 5.3 策略关系如何参与复用决策

规划器先读取完整关系模型，为每项义务提取行为依赖切片。切片包含可能改变触发或结果的前序规则、共同生效指令、引用和联合约束，而不只是当前策略节点。

随后生成候选请求，检查它在完整选择组中实际会选中哪条规则，再建立“探针可以支持哪些义务”的覆盖关系。只有有依据的候选获得复用许可；未支持或无法确认的项保留为未知，不从义务集合删除。

例如，同一路由的目标选择和 Header 操作，在请求、配置和阶段兼容且证据充分时，可以复用一次请求，再分别判定。前后路由互相遮蔽时，一个请求不能冒充两条路由都已执行。重试恢复与总预算截断需要不同触发时，也不能互相替代。

复用准入主要检查：

1. 每项义务所需行为是否仍能被实际触发。
2. 有效配置、负载和状态前提是否保持。
3. 是否能够依据完整证据分别判定各项断言。
4. 是否符合具有明确适用范围和验证依据的复用规则。

多策略组合整体检查，不能仅凭两两兼容批准更大的组合。检错能力保持需要独立与复用方案的缺陷对照；有限故障集合上的结果不能推广为普遍保证。

### 5.4 执行与证据判定

执行记录关联运行 ID、参照模型摘要、探针 ID、执行 ID、请求 ID、配置代次和时间。同一记录可以被多个义务引用，引用不会消耗证据。

可信反证应使对应义务 FAIL；缺少证据、错误运行、陈旧事件、请求不符或上下文歧义应保持 INCONCLUSIVE。某个错误配置被检出，不代表其所有其他义务都完成验证。

纯 Python 规划与判定可以使用可选进程后端；集群修改和流量仍由受约束的调度器管理。计算并行不能绕过资源锁。

### 5.5 冲突感知调度具体怎样运行

这里的任务是一次探针执行及其采集、判定和恢复过程。调度器安排哪个任务何时运行；它本身不减少验证义务，也不把多个探针合成一个。

**先检查冲突，再分配线程。** 每个任务声明自己需要读取或修改的配置、会影响的共享状态以及观测范围。调度器只把当前可以安全运行的任务提交给 worker。有冲突的任务留在待运行队列，不分配一个线程让它一直等锁；队列后面没有冲突的任务可以先运行。

检查的具体含义如下：

- 配置：A 正在修改某个 VirtualService 时，依赖该配置的 B 需要等待；两者都只读且没有其他冲突时，可以共享读取。
- 共享状态：两个任务如果使用同一个连接池或限流额度，即使请求 ID 不同，也可能改变对方的测试条件，需要隔离或专门的并发许可。
- 负载：多个任务同时发请求不能超过事先允许的负载范围，以免并发本身触发额外超时或熔断。当前实验采用固定且经过测试的负载范围，通用自动容量准入仍待实现。
- 观测：能够用请求 ID 等可靠标识分别归因时，才考虑并行；只有无法区分来源的服务级汇总指标时，仍保留观测互斥。不同服务名称也不自动代表独立，还要检查共享下游和其他状态。

**等待观测时，把线程让给其他任务。** 请求发送完后，如果还需要等待指标可见或后端尝试结束，任务记录下一次检查时间或截止时间，暂时退出线程池。到时再由调度器安排继续采集和判定。当前按时间唤醒不等于已实现所有遥测源的事件通知，也不表示到时一定拿到了完整证据。

**让出线程，不等于解除隔离。** 等待期间仍保留必要的配置和状态预留，防止其他任务改动配置或污染结果。采集、恢复及必要的后端收尾完成后，才释放相应预留。

例如，队列中有三个任务，只有一个执行线程：

```text
A  修改 reviews 的配置，发送探针，然后等待观测
B  也需要修改同一个配置，与 A 冲突
C  验证另一独立目标，已确认配置、状态和观测均与 A 隔离

运行过程
A 发送完请求并进入等待，暂时让出执行线程，但保留资源锁
B 因为配置冲突留在队列中，不占线程
C 使用空出的线程执行
A 到达检查时间后恢复执行，采集、判定并恢复配置
A 释放资源后，B 才具备运行条件
```

多个 worker 时，同样的规则决定哪些任务可以同时执行。因此，这项优化省下的是本来可以重叠的排队与等待时间，不会消除策略本身必须保留的观测窗口。若所有剩余任务都冲突，线程空闲也是正常的，不能为了提高利用率提前释放保护。

### 5.6 当前实现边界

当前已提供显式义务规划入口、有限探针复用、逐义务证据判定，以及受控串行和并发实验。路由、Header、改写及部分统计或状态策略使用明确的受控契约，不是任意业务环境的通用执行许可。

目前共享的是符合合同的探针证据，尚未自动合并生产 Envoy 日志或 Prometheus 采集会话。生产采集适配、默认 Web 流程的完整接入和自动容量准入仍需完善。

## 6 创新点四 配置依赖图与诊断

### 6.1 解决的问题

异常可能跨越配置资源、策略和服务。单条告警难以说明它与哪些规则有关、哪些服务可能受影响，以及哪些静态或动态证据支持这一判断。

依赖图需要明确区分配置引用、策略语义关系、服务调用和跨层证据关联，避免将所有连线都解释为同一种依赖。

### 6.2 拟实现的方法

图中保留配置资源、策略规则、数据面实现、服务或实例，以及验证义务和证据的关联。声明关联与实际观测关联分别标记，未知或未观测的边不能伪装成已确认的调用。

诊断从失败义务出发，沿来源和实现关联找到相关配置，再结合策略关系生成根因候选；沿配置作用范围及服务依赖分析潜在影响。每个候选附带可追溯的证据路径。

关系模型负责解释有效行为，依赖诊断负责组织异常来源和影响。图中的策略关系应复用统一模型产物，避免再维护一套不同的语义定义。

### 6.3 当前边界与评价要求

当前已具备配置、策略、义务与证据关联，以及按依赖距离组织的资源候选。真实调用归因、因果定位和影响识别仍需完善；图可达性不自动等于真实因果关系。

若将其列为独立贡献，需要评价根因候选 Top-1、Top-3 命中率，以及受影响服务识别的 Precision 和 Recall，并与告警列表、直接引用关系等方法比较。若定位算法和实验尚不足，应将其表述为辅助诊断能力。

## 7 四项创新之间如何联系

```text
全链路验证：声明配置 → 数据面规则 → 运行行为
                         │
                 跨层统一语义模型
                 ┌───────┴────────┐
          静态实现一致性检查       动态验证义务
                 ↓                ↓
              静态结论       低开销规划与执行
                 │                ↓
                 │           运行证据与动态结论
                 └───────┬────────┘
                   阶段关联与结果解释
                         ↓
                  配置依赖图与诊断
```


全链路验证定义整体边界、各阶段所需证据及阶段结果关联；统一模型提供一致的行为解释；验证规划在保留义务的前提下减少工作；依赖诊断将差异和证据关联回配置、策略和服务。

| 连接 | 传递的内容 | 作用 |
|---|---|---|
| 语义模型 → 静态验证 | 策略、关系、有效范围和行为 | 识别缺失、错误和额外生效行为 |
| 语义模型 → 验证规划 | 触发条件、依赖切片和未知项 | 生成有效探针并约束复用 |
| 验证规划 → 分阶段判定 | 计划、执行记录和证据质量 | 区分通过、失败和未能判定 |
| 模型与判定 → 依赖诊断 | 来源、实现关联、失败义务和证据 | 解释根因候选及潜在影响 |

参照模型与被测状态必须分开保存。故障实验固定声明期望，只改变被测状态；不能根据错误状态重新生成“正确答案”。实际证据也用于检查探针是否真正执行了计划，而不是只凭计划覆盖就宣布验证完成。

## 8 当前实现与建议实施顺序

### 8.1 当前状态

下表依据现有代码、实现说明和已保存报告整理，不表示重新执行了全部测试。

| 能力 | 当前状态 | 仍需补充 |
|---|---|---|
| 全链路阶段编排 | 静态对齐与动态义务各自可执行 | 稳定策略身份、范围与版本关联，以及同一运行内阶段结果汇总 |
| parser 关系参照模型 | 已有原始快照到关系模型的显式产物 | 完整数据面关系投影与字段级继承解释 |
| 验证义务与行为切片 | 已有规划、候选及三态覆盖决策 | 更完整的条件语义和关系义务 |
| 有限探针复用与判定 | 已有显式 CLI 和受控后端证据对照 | 生产采集合同适配与更多独立缺陷 |
| 流量 worker 调度 | 已有资源预留、就绪队列和等待让出线程 | 默认流程与新证据能力的完整联动 |
| 计算并行 | 已有可选线程和进程接口 | 更多规模下的成本与收益验证 |
| 原生采集共享 | 尚未完成通用实现 | 日志游标、查询合并、完整性及新鲜度管理 |
| 依赖诊断 | 已有证据关联图和依赖距离候选 | 因果定位、实际影响识别及定量评价 |

验证规划通过统一 CLI 和默认 Web API 使用；受控执行须显式指定 `--execute`，并提供后端契约和配置代次条件。矩阵兼容路径中的重试、连接池及熔断 VS 注入已被禁用，能力不足的项保留为 INCONCLUSIVE。服务器验证使用独立源码副本，运行中的远程 Web 未覆盖部署。见 [受控触发说明](CONTROLLED_STIMULUS_VALIDATION.md)。受控后端具有逐请求回执能力，不代表标准 Prometheus 已具备用例标签。

### 8.2 建议实施顺序

1. 明确支持范围，补齐策略来源、关系含义和静态比较边界。
2. 固定独立探针基线，完善策略专属 Oracle、触发确认和证据质量判定。
3. 扩展有限复用规则，保持逐义务缺陷对照和未知项追踪。
4. 实现生产采集适配及共享采集，再按真实隔离能力放开并发。
5. 完善阶段衔接和默认入口，避免实验接口与产品流程长期分离。
6. 增加依赖诊断算法与评价，再确定第四项贡献的主张强度。

## 9 实验依据与后续评价

### 9.1 已有实验能够支持什么

以下数据来自 2026 年 11 月 5 日至 6 日的受控实验记录。各批次配置、源码版本、计时范围和缺陷集合不同，应分别引用，不直接合并成总体准确率。

| 实验 | 已有观察 | 结论边界 |
|---|---|---|
| 复杂策略串行对照 | 26 种错误配置各重复 3 次，独立与复用均检出 78/78；30 次正常配置成对试验未观察到误报 | 只支持该有限缺陷集；错误配置中仍有明确保留的 INCONCLUSIVE 义务 |
| 复杂策略工作量 | 152 项义务保留，逻辑探针 152→35，单轮 HTTP 566→449 | 逻辑探针减少约 77.0%，实际请求减少约 20.7%，不能混为一个指标 |
| 纯路由大规模并行 | 256 条规则、1024 项义务，复用方案 1→4 流量 worker 执行中位数 6.275→1.642 秒 | 约 3.82 倍为执行阶段加速，不是端到端加速 |
| 纯路由完整链路 | 重新规划、执行、判定及写盘合计 10.794→4.673 秒 | 使用 2 个计算进程和 4 个流量 worker；静态解析与配置下发在准备阶段单列 |
| 多服务混合配置 | 72 个业务 Service 场景中，单轮 HTTP 2742→1662；复用 1→4 worker 执行中位数 20.611→5.915 秒 | 请求减少 39.39%，固定复用后的并发加速约 3.48 倍；不是完整链路计时 |

多服务实验中，两批组合缺陷的重复对照，每种方案均检出 1320/1320 项预设缺陷实例。它们不是 1320 种独立故障，且故障配置下部分相关义务仍为 INCONCLUSIVE，因此不能据此报告全局 100% accuracy 或普遍检错保证。

受控服务由专用后端承载，真实请求经过网关，但尚不能代表真实应用 Pod 调用链的全部行为。样本、时间容差和固定统计容差仍需进一步给出理论依据与敏感性分析。

### 9.2 后续应如何评价四项贡献

| 方法 | 需要补充的对照 | 主要指标 |
|---|---|---|
| 全链路验证 | Static-only、Dynamic-only、Hybrid；正常配置、更新及未收敛场景 | 分类型检出、误报、漏报、未判定及发现时间 |
| 关系语义模型 | 属性匹配与关系解析；顺序、覆盖、残留及作用范围案例 | 差异识别、反例有效性、支持范围和未知比例 |
| 低开销规划 | 独立基线、仅探针复用、仅采集共享、仅调度及组合方案 | 逐义务检出保持、实际请求、查询、配置操作和时间 |
| 依赖诊断 | 告警列表、直接引用图与完整关联图 | Top-1/Top-3、影响范围 Precision/Recall、定位耗时 |

低开销实验需要分别报告逻辑探针数、实际下游请求数、上游尝试数、采集调用次数和总时间。分流样本、状态触发负载和必要窗口不能为追求减少率被直接删除。

时间应拆分解析、规划、配置就绪、执行、等待、采集、判定和写盘，并单独重复测量完整链路。不能把各阶段中位数相加充当端到端结果。

线程主要用于重叠网络与观测等待，进程用于可独立计算的规划或判定。CPU Time 与 Wall Time 分别记录，不能根据一个核心的占用直接推断整个动态验证受 Python 单线程限制。

与相关工具比较时，应使用一致的故障集合和适用条件，区分配置错误、跨层偏差、运行时异常和依赖问题。受控变异之外还需补充可复现的真实问题与独立测试集。

## 10 论文贡献表述建议

以下表述用于组织下一版论文；最终应按实际实现与实验范围收紧。

1. 提出面向服务网格配置的全链路验证方法，关联声明配置、已安装规则与运行行为，并结合策略专属判定和证据质量检查识别跨阶段偏差。
2. 提出跨层统一语义模型，在 PAOC 单策略表示之上显式建模选择顺序、引用、继承覆盖及联合约束，在受支持范围内分析有效行为与跨层差异。
3. 提出低开销验证规划，通过条件式探针复用、采集共享和冲突感知调度，减少重复工作，并对各验证义务保留独立判定与检错对照。
4. 设计配置依赖图与诊断方法，连接配置、策略、数据面实现和服务依赖，为根因候选及潜在影响提供可追溯解释。

其中，第二项为语义基础，第三项为效率方法。第一项需要以阶段衔接和 Oracle 体现方法深度；第四项需要算法与定量实验支撑。未完成的内容应作为后续工作，不能仅凭改名视为已完成贡献。

## 11 后续修改需要明确的问题

- 论文将支持哪些策略、匹配条件和关系，哪些明确返回未知？
